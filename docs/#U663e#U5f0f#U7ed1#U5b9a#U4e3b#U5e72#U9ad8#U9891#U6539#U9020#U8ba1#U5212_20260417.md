# 显式绑定主干高频改造计划

## 记录时间

- 2026-04-17

## 这轮改造要解决的核心问题

当前 `multiview explicit_binding` 主线的剩余清晰度 gap，已经基本收束到：

- 不是继续缺一个更细的 ROI
- 不是继续缺一个更硬的局部 high-frequency loss
- 不是继续缺一个更重的 boundary-safe 或 torso-core 小补丁
- 而是当前 `texture / carrier` 的高频表达路径本身还不够强

更具体地说：

- 现在的 `structured_trunk` 主要还是往 `base MLP` 输入里加 residual delta
- 后面的 `detail_high_frequency / face_branch` 也主要是输出端 capped residual repair
- 这会导致 trunk 学到的信息最后仍然要挤进同一个浅层颜色主头里解码
- 高频很容易在最后这一步被重新抹平

因此这轮不再沿着“再补一个局部监督补丁”的方向走，而是直接把 trunk 往真正的 appearance 主干改。

## 这轮新主线的目标

目标不是再做：

- `base_color + 一堆 capped residual`

而是逐步改成更接近下面这个结构：

- `final_color = base_color + trunk_color * trunk_gate + tiny_repair`

对应到实现层面：

- `base_color`
  - 继续由当前稳定的 `base MLP` 负责
  - 主要承载低频主体颜色、整体视角一致性和基础外观
- `trunk_color`
  - 由新的 trunk output head 直接预测
  - 主要承载 shoulder / upper-torso / drawstring / body-cloth separation / face 等位置的中高频
- `trunk_gate`
  - 由 trunk 自己预测的 soft gate 控制
  - 尽量避免继续依赖 output 端的硬 point gate 去裁残差
- `tiny_repair`
  - 保留当前 `detail_residual / high_frequency` 体系
  - 但在新主线里把它降级成轻量修补分支，而不是主要清晰度来源

## 代码层面的直接改造方向

### 1. 在 `models/texture/texture.py` 中新增 trunk output head

核心要求：

- 新增 `trunk_rgb_head` 或等价的 trunk output head 配置能力
- trunk head 不再只是往输入特征里打一层 delta
- 而是直接预测一条 trunk appearance residual
- 这条 residual 在 forward 中以 `base_output + trunk_output * trunk_gate` 的方式参与最终颜色输出

预期收益：

- 让 explicit_binding 主干自己承担一部分高频生成责任
- 不再把主要高频恢复任务压给 late repair branches

### 2. 把 trunk 的信息注入方式从 `features + delta` 往 `concat / fusion` 推

当前问题：

- `structured_trunk` 的 shared / structure / local 信息，大多是先被压成 delta
- 再加回 `features`
- 最后统一交给原来的浅 `base MLP`
- 这会让 trunk 信息在最后一段解码里继续被平均化、平滑化

这轮改造方向：

- trunk output head 直接吃 fusion input
- fusion input 由以下几类信息拼接而成：
  - base input features
  - shared trunk carrier 的融合特征
  - structure carrier 的融合特征
  - region-local carriers 的融合特征
- 不再只依赖“先加回输入、再统一解码”的单一路径

### 3. 把 shoulder / torso 这类 body 高频从 output 端硬 gate 往 feature 端软条件迁移

当前问题：

- 现有很多 local carrier / high-frequency branch 仍然依赖 output 端乘 point gate
- 这类 hard gating 更像“截断”或“修补”
- 不像真正的 region-aware appearance generation

这轮改造方向：

- 尽量少在 trunk output 最后一层乘硬 point gate
- 尽量把 region 信息提前到 trunk fusion input 侧
- 让 shoulder / upper-torso / face 这些局部高频作为 soft condition 进入 trunk head
- trunk gate 只负责软分配，不负责硬裁剪

## 这轮改造的实现策略

为了不破坏现有稳定主线，这轮代码采用兼容式改造：

- 默认不改变旧配置行为
- 新 trunk output head 通过配置显式开启
- 旧的 `structured_trunk input residual` 路径仍保留
- 但新增配置可以在启用 trunk output head 时关闭旧的 input residual 路径

这样做的好处是：

- `v117b` / `v118b` 这类稳定 resume 线不会因为代码更新直接失效
- 可以先在同一套代码下做 trunk-output-head 与旧 trunk-delta 路径的可控对比

## 实验策略

后续实验优先级明确如下：

### 主基线

- 继续以 `v117b` 这类 resume 稳定版为工作基线

原因：

- 它已经证明 resume 线是当前最稳、最接近可用主线的方向
- 结构稳定、边界没有 fresh 线那种明显发花或破损

### 不优先的方向

- 暂时不把主要预算继续压在 fresh-from-zero fullstack 上

原因：

- `v119a / v119b` 已经说明当前 fresh fullstack 训练动力学还不稳定
- 在表达路径没有真正改强之前，继续加 fresh 容量更容易把错误纹理学重

### 本轮最值得验证的点

1. trunk output head 开启后，是否能在不破坏稳定性的前提下，明显提升：
- 脸部轮廓和五官明暗转折
- shoulder / upper-arm 边界利落程度
- upper-torso cloth folds
- drawstring / body-cloth separation

2. 新 trunk fusion 路径是否真的能把 trunk 信息保留下来，而不是继续被 base MLP 抹平

3. 在 trunk head 生效后，late high-frequency branch 是否可以进一步降级成 tiny repair，而不会立刻掉清晰度

## 这轮完成后希望得到的状态

理想状态不是立刻“全局完全追平 baseline”，而是先出现下面这类信号：

- 肉眼上第一次出现比 `v117b` 更明确的清晰度前进
- 提升不再只集中在脸部，而是能同时出现在 shoulder / torso / drawstring 一带
- 改动的收益主要来自 trunk 主干，而不是再次依赖 late-stage 局部修补

## 一句话总目标

> 这一轮的重点，不是继续在 ROI / boundary / core-supervision 上小修小补，而是把 `explicit_binding` 这条主干真正改造成一条“自己能长出高频”的 appearance 主线，让 trunk 不再只是补丁，而是成为清晰度恢复的主要承载路径。

### 机制对比

`v166c` 的问题不是 support 不够，而是 trunk 主干高频动态跑偏。

- `v166c @2000`
  - `support = 0.9194`
  - `head_gate = 0.9915`
  - `owner_takeover = 0.5328`
  - `boundary_takeover = 0.0357`
  - `boundary_focus = 0.0215`

这说明 `v166c` 不是“trunk 主干自己长出高频”，而是 trunk gate 接近全开后和 owner head 一起把外观重新平均化。继续加 boundary 或继续加 owner 都不是根因修复。

### 当前路线调整

接下来回到 `v142e / v139a / v136a` 这条清晰成功线，把它作为显式绑定主干高频的机制锚点。

目的不是继续在 `v142e` 上做局部补丁，而是复核并固化它的清晰机制：

- 保留 `v142e` 的 signed contour 和 selective trunk 状态；
- 不从 `v166c` 续训；
- 不重开 densify / opacity reset / binding-state reset；
- 不再优先加强 boundary head；
- 先验证 local color 能不能进入 trunk HF 主路径，而不是被 late repair 或 owner branch 代替。

## 2026-04-26 补充：v170 批处理计划

### 代码修复

已在 `models/texture/texture.py` 增加 boundary head 的 focus source 配置：

```yaml
model:
  texture:
    structured_trunk:
      output_head:
        local_color:
          owner:
            head:
              boundary:
                focus_source: boundary_tag
```

默认仍是旧行为 `score`。当设置为 `boundary_tag` 时，boundary head / boundary takeover 直接使用已经收窄后的 Gaussian boundary tag 作为激活区域。这个修复针对 `v169a` 的断点：tag 已经是 8%，但 focus 被连续分数和 gate 稀释到约 0.014。
