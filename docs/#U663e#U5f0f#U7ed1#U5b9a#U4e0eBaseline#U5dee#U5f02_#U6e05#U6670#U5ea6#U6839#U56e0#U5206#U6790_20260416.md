## 这次要回答的两个核心问题

### 问题 1

用户提问：

> 我当前这个项目和baseline现在根本就不是同一个技术方面的项目了？不存在先生成高斯然后再去绑定到特定的位置，而是先绑定完位置再去生成高斯？

结论：

- 不是“先绑定完位置再生成高斯”。
- 当前主线和 baseline 仍然属于同一个大框架：都是先在 canonical 空间里初始化高斯，再通过 deformer 把高斯变到当前帧位置，再渲染。
- 但两者不是同一条 rigid deformation 技术线。

关键代码依据：

- 高斯初始化仍然是先从点云创建：
  - `/remote-home/ming/3dgs-avatar-release-main/scene/__init__.py`
  - `/remote-home/ming/3dgs-avatar-release-main/scene/gaussian_model.py`
- 主流程仍然是：
  - 先有 canonical 高斯
  - 再经过 `non_rigid`
  - 再经过 `rigid`
  - 最后进入 texture / render
  - 对应：
    - `/remote-home/ming/3dgs-avatar-release-main/models/deformer/deformer.py`
    - `/remote-home/ming/3dgs-avatar-release-main/models/gaussian_converter.py`

更准确地说：

- baseline 参考目录：
  - `/remote-home/ming/3dgs-avatar-release-main/exp/baseline/zju_377_mono-direct-mlp_field-ingp-shallow_mlp-baseline_15k_main`
- 它对应的 rigid 技术线是：
  - `mlp_field / skinning_field`
- 文档中 baseline 的训练命令也明确写的是：
  - `rigid=mlp_field`
  - 对应：
    - `/remote-home/ming/3dgs-avatar-release-main/docs/NEXT_EXPERIMENT_PLAN.md`

所以正确表述应当是：

> 当前主线和 baseline 不是“先后顺序不同”的两套项目，而是“同一训练框架下，两条不同 rigid deformation 实现”的两条技术路线。

### 问题 2

用户提问：

> 那我explicit_binding设计成结构更稳了，但肩膀、上臂、脸和躯干细节更软，这个能不能修复就是要提高一下清晰度

结论：

- 能修。
- 但不能只把它理解成“继续提一点纹理清晰度”。
- 当前更像是：
  - 绑定结构本身会压掉一部分 `non_rigid` 学到的细节
  - 再叠加 appearance carrier 偏保守
  - 最后共同表现成“结构更稳，但肩膀、上臂、脸和躯干更软”

所以这不是单纯的后端清晰度问题，而是：

> 先有结构侧的 detail loss，再有外观侧的高频不足。

## 关键技术判断

### 1. baseline 和 explicit binding 本来就不等价

为了避免一直拿错对比对象，这里把本地已存在的 CoreView_377 结果重新核了一遍：

- baseline
  - `/remote-home/ming/3dgs-avatar-release-main/exp/baseline/zju_377_mono-direct-mlp_field-ingp-shallow_mlp-baseline_15k_main/test-view/results.npz`
  - `psnr=30.524714`
  - `ssim=0.977174`
  - `lpips=0.021162`
- mono explicit binding v3
  - `/remote-home/ming/3dgs-avatar-release-main/exp/experiment/zju_377_mono-direct-explicit_binding-ingp-shallow_mlp-expbind_v3_15k-0311-0717/test-view/results.npz`
  - `psnr=29.820358`
  - `ssim=0.974385`
  - `lpips=0.025762`
- mono explicit binding v4.1
  - `/remote-home/ming/3dgs-avatar-release-main/exp/experiment/zju_377_mono-direct-explicit_binding-ingp-shallow_mlp-bodycloth_v41_15k-0311-1123-main/test-view/results.npz`
  - `psnr=29.908655`
  - `ssim=0.974485`
  - `lpips=0.025616`

这说明：

- 即使在更早的 mono 线里
- `explicit_binding` 也没有天然稳定压过 `mlp_field baseline`

因此当前多视角结果一直比 baseline 软，不一定意味着“最近把显式绑定写坏了”，更可能意味着：

- baseline 这条 `mlp_field` 路线本来就更容易保住细节
- `explicit_binding` 则天然更保守、更稳、更容易软化

### 2. 当前没有看到新的“显式绑定主逻辑硬 bug”

目前重新核查后的判断是：

- 没有看到那种会直接导致结果异常掉清晰度的显式绑定主逻辑硬 bug
- 之前真正查出来的硬 bug 是 fresh train 时 densify 后 residual 状态没有同步回写
- 但那个 bug 不在 `explicit_binding` 主逻辑里

对应文档记录：

- `/remote-home/ming/3dgs-avatar-release-main/docs/项目.md`

### 3. 但当前 `explicit_binding` 存在一个最像根因的结构问题

这次重新看代码后，最像根因的不是阈值，而是 rigid / non-rigid 的衔接方式。

当前 deformer 顺序是：

1. 先做 `non_rigid`
2. 把原始 canonical 位置存成 `canonical_xyz`
3. 再做 `rigid`

对应：

- `/remote-home/ming/3dgs-avatar-release-main/models/deformer/deformer.py`

`non_rigid` 已经会先把位置改成：

- `gaussians._xyz + delta_xyz`

对应：

- `/remote-home/ming/3dgs-avatar-release-main/models/deformer/non_rigid.py`

但 `explicit_binding.forward()` 里：

- binding 是基于 `canonical_xyz` 建的
- `x_rigid / x_soft` 主要沿 canonical anchor 和 canonical local offset 来走
- 只有 `x_free` 明显直接吃到了当前 `xyz`

对应：

- `/remote-home/ming/3dgs-avatar-release-main/models/deformer/rigid.py`

这会造成一个很关键的副作用：

- `non_rigid` 学到的位移
- 在大量被判成 `rigid / soft` 的点上
- 并没有完整 carry 到最终位置

于是表现就会很像：

- 结构稳定了
- 但肩膀、上臂、脸、躯干这类本应靠 non-rigid 补出来的局部细节被压掉了
- 最后视觉上变成“稳但软”

这不是报错级 bug，但它非常像：

> 一个会系统性吃掉细节的结构性实现问题。

## 为什么只提高清晰度还不够

如果只做 texture / perceptual / local carrier 这类清晰度增强，会发生：

- 颜色和高频纹理也许能更锐一点
- 但被 rigid / soft 分支吃掉的位置细节仍然回不来

因此它的修法应该分两层：

### 第一层：先修结构

目标：

- 让 `non_rigid` 学到的位移不再只在 `free` 分支有效
- 而是能按可控强度 carry 到 `rigid / soft` 分支

这样修完后，理论预期是：

- 肩膀和上臂不会再那么容易“厚、虚、羽化”
- 脸和躯干一些被稳态抹掉的细节可以重新保住
- 同样的 appearance supervision 会更有效

### 第二层：再修清晰度

在结构侧不再吃细节之后，再继续做：

- parser ROI
- face / torso / shoulder 的局部高频监督
- carrier 放松
- opacity micro-sharp

这些清晰度手段才会真正长在对的地方。

## 这轮代码修复的目标

这次不再继续做“只调阈值”的小修小补，而是直接改最像根因的结构点：

- 在 `explicit_binding.forward()` 中
- 显式提取 `xyz - canonical_xyz` 的 non-rigid 位移
- 不再只让它在 `free` 分支里生效
- 而是按可控强度 carry 到 `rigid / soft` 分支

这次计划做两版实验：

- `v113a`
  - 保守 carry
  - 目标是先验证不会破坏当前 `v110b` 的稳定结构
- `v113b`
  - 更强 carry
  - 目标是验证结构性 detail recovery 的上限

## 这轮判断的最终一句话总结

> 当前和 baseline 的差距，不是“先绑定后生成高斯”这种流程差异，也不是一个新的显式绑定硬 bug，而更像是：`explicit_binding` 这条路线本身更保守、更稳，同时在 rigid / soft 分支里没有把 non-rigid 学到的细节完整 carry 下来，于是结构更稳了，但局部细节被系统性抹软了。真正值得优先修的，是这个结构衔接问题，而不是继续只在清晰度损失上做小扫参。

## 2026-04-17 补充更新：经过 `v113 -> v123` 后，对上面结论的修正

上面这份判断写下时，`v113a / v113b` 还只是“准备验证的下一步”。现在这条线已经往后连续跑到了 `v123`，因此需要把结论更新到当前阶段。

### 1. 当时怀疑的“结构侧偷细节”不是误判，而且已经被验证过

后续 `v113 -> v117` 这几组实验，基本把这件事验证实了：

- `v113`
  - `non_rigid carry` 方向成立
- `v114`
  - `geom-aware safe` 比更激进的 `sharp` 更稳
- `v115 -> v117`
  - `structure bridge / trunk main / trunk mlp` 把结构侧的主逻辑一步步理顺

关键结果可以简记为：

- `v115b`
  - render `PSNR=32.2641`
  - render `LPIPS=0.022970`
- `v117b`
  - render `PSNR=32.2944`
  - render `LPIPS=0.023031`

这说明：

1. 之前说的“`rigid / soft` 分支会偷吃一部分细节”是对的

2. 结构侧确实需要修
- 不修的话，后面的清晰度增强很多都会长歪

3. 但修完结构侧之后，baseline gap 仍然还在
- 这说明它不是唯一根因

### 2. 因此，当前最强根因已经不再是“显式绑定主逻辑写错了”

在 `v117b` 这类稳定主基线出来之后，可以更明确地说：

- 当前没有看到新的、能一锤定音解释所有 softness 的 `explicit_binding` 主逻辑硬 bug
- 结构侧的问题更像“会系统性吃掉一部分细节的实现偏保守”
- 这部分现在已经被大幅理顺，但没有把 baseline 清晰度差距自动补平

所以当前最像根因的部分，已经从：

- “结构衔接有问题”

进一步更新为：

- “appearance / trunk 主干自己的高频表达路径还不够强”

也就是说，问题已经从：

- 细节先被结构偷掉

进一步推进到：

- 即便结构不再明显偷细节，主干自己也还没有足够强地把高频长出来

### 3. `v121a / v122a` 标志着主线已经从“修补高频”转向“主干自己长高频”

这是这轮更新里最关键的一点。

后续主线没有再继续把预算主要投到：

- 更细 ROI
- 更重 boundary-safe
- 更重 torso-core patch

而是直接把 `texture / trunk` 往真正的 appearance 主干改。

对应的关键版本是：

- `v121a`
  - 第一次把 trunk 从“输入 residual”往“输出颜色头”推进
  - render `PSNR=32.3267`
  - render `LPIPS=0.023063`
- `v122a`
  - 进一步形成 `base_color + trunk_color * trunk_gate + tiny_repair`
  - render `PSNR=32.3269`
  - render `LPIPS=0.022962`

这两版说明：

1. 当前主线已经不再只是“修补支路在补高频”

2. `explicit_binding` 这条 trunk 已经开始自己承担外观和中高频

3. 但它还没有完全到“纯 trunk、完全去掉旧 tiny repair、并且质量追平 baseline”的终局状态

更准确地说，当前状态应表述为：

> 结构上，已经基本进入“主干自己长高频”的完整路线；但质量上，还没有到“纯 trunk 最终版”。

### 4. 所以，如何回答前面那两个问题，现在可以更完整地更新

#### 对问题 1 的更新回答

问题是：

> 当前这个项目和 baseline 现在根本就不是同一个技术方面的项目了？是不是先绑定完位置再去生成高斯？

更新后的结论仍然是：

- 不是“先绑定完位置再生成高斯”
- 当前主线和 baseline 仍然是同一个大框架：
  - 先有 canonical 高斯
  - 再做 deformer
  - 最后做 texture / render
- 但两者不是同一条 rigid deformation 技术线

因此最准确的说法仍然是：

> 这不是两种完全不同技术范式的项目，而是同一 canonical-GS-to-deform-to-render 框架下，两条不同 rigid deformation 路线。

#### 对问题 2 的更新回答

问题是：

> `explicit_binding` 设计成结构更稳了，但肩膀、上臂、脸和躯干细节更软，这个能不能修复？是不是就是要提高一下清晰度？

更新后的结论是：

- 能修
- 但它不只是“加点清晰度 loss”这么简单

更准确的分层应该是：

1. 前半段问题已经被 `v113 -> v117` 证明并部分修复
- 结构侧确实会偷细节
- 这部分不理顺，后面的高清晰度很难长对位置

2. 后半段才是现在真正剩下的主战场
- `explicit_binding` 主干自己的高频颜色路径还不够强
- 尤其是 face、jawline、shoulder-neck、torso cloth fold、body-cloth separation 这些地方

所以当前的说法应该更新成：

> 不是“结构更稳了，所以只要再加一点清晰度就行”，而是“结构侧已经大体理顺，现在真正还差的是让 explicit_binding 这条主干自己稳定地长出足够强的高频外观”。

### 5. 当前阶段的一句话最终结论

> 现在回头看，最开始把问题指向 `explicit_binding` 的结构衔接是有价值的，因为它确实揭示了细节被吃掉的一层根因；但经过 `v113 -> v123` 的连续实验后，当前最核心的剩余问题已经不再是“显式绑定是不是写错了”，而是“这条 explicit_binding 主干自己的 appearance / high-frequency path 还不够强”。也正因为如此，主线才会从结构修补，进一步转向 `v121a / v122a / v123` 这种“让主干自己长高频”的改造。

- 旧 seed 依赖是真的
- legacy 路径残留也是真的
- 但单独修这两件事，都还不能把脸、肩颈、上臂、领口、躯干分离这些高频一把拉起来

所以到 `v135` 为止，最像根因的表述已经要进一步更新成：

> 当前最大的问题，不再是 `explicit_binding` 有没有明显写错，也不只是 old seed / legacy residual 有没有残留，而是 owner 这条 trunk 主干虽然越来越负责关键区域最终颜色，但还没有被足够直接地训练成关键区域的高频主输出路径。

### 3. 当前仍未解决的问题，到这一步应该怎么概括

截至 `v136` 之前，当前卡住的问题可以更具体地写成下面几条：

1. 主干逻辑已经越来越顺，但脸、肩颈、上臂、领口、躯干布料分离这些地方的高频还是只提了一小截
- 视觉上更像：
  - 结构更稳
  - 区域责任更清楚
  - 但边缘还不够硬、纹理还不够利、body-cloth separation 还不够干净

2. 现在不太像还有一个新的显式绑定硬 bug 没查出来
- 更像是：
  - owner 已经开始接管最终颜色
  - 但训练目标还没有持续、直接地逼它把高频自己长硬

3. old coarse / hf trunk 的影响还没有完全退场
- 尤其在 `v135b / v136b` 里能持续看到：
  - legacy 路径还保留一部分权重
  - 这会让 owner 更容易学成“稳稳接管”，而不是“强高频接管”

4. 当前关键区域虽然比以前清楚得多，但对更细粒度的位置仍然不够细
- 当前主打的还是：
  - `face`
  - `shoulder_arm`
  - `upper_torso`
  - `upper_torso_core`
- 对发际边缘、袖口、肩带边、领口折线、上臂外轮廓这些高频更敏感的位置，当前 supervision 还不算足够精细

### 4. `v136a / v136b`：第一次不只改 blend / gate，而是直接改训练目标，让 owner 接管越强，局部高频监督越重

  - local detail

### 6. 当前要做的事，不应该再是小修小补，而是转成下面 4 条结构主线

这一段是当前待做主线，也是一会儿后续实验和代码改造应当围绕的方向。

#### 方向 1：把 boundary 问题从 texture 问题升级成 silhouette / geometry 问题

当前 `v138a` 改的是 owner boundary color head，但真正决定外轮廓清不清楚的，主要还是：

- `opacity`
- `scaling`
- `rotation`
- `xyz`

因此下一步不应再优先继续叠 texture boundary head，而应优先转到：

- boundary-only `opacity residual`
- boundary-only `scaling residual`
- 必要时少量 `xyz / rotation` 边界微调

也就是说，下一轮真正该接管 hardest contour 的，不是 `boundary_color`，而是 boundary geometry / alpha 分支。

#### 方向 2：把 boundary supervision 从“detail interior 顺带覆盖”改成独立 edge expert supervision

当前配置里长期存在的问题是：

- `detail_interior_exclude_boundary_width=7`
- 多个 region 的 `detail_boundary_keep_weight=0.0`
- `lambda_mask_boundary_hard=0.0`
- `lambda_silhouette_outer=0.0`

这导致最硬、最窄、最影响观感的 boundary band，并没有被主监督持续强压。

下一步应改成：

1. 单独建立窄 boundary band 监督
2. 对 boundary band 做 top-k hard mining
3. 把 patch perceptual / gradient / mask boundary / silhouette loss 显式压到 hardest contour 上
4. 不再默认把 boundary 从 detail 主监督里排掉

#### 方向 3：把 boundary gating 从 detached binding prior 改成 image-error-driven

当前 boundary 相关路由很多仍然是：

- 来自 `binding_boundary_score`
- 还是 detach 的
- 再经过 threshold / power / gate 压一层

这意味着：

1. 系统主要是在相信先验“哪里像边界”
2. 而不是根据 render-vs-GT 的真实边界误差去学习“哪里必须更硬”

下一步应把 boundary subset / boundary tag / boundary routing 改成更强的 image-error-driven 方案：

- 用 boundary disagreement 更新子集
- 用 hardest boundary patch 决定哪一批点真的要承担边界责任
- detach prior 只做初始化或上限，不再做唯一裁判

#### 方向 4：简化最终混合逻辑，不再让 boundary expert 只能做一个很弱的 bounded replacement

当前这条主线的问题之一是：

- coarse
- hf
- owner
- owner-boundary
- tiny repair

叠加之后，最后常常还是一个偏保守的平滑混合器。

下一步应尽量转成更直接的结构：

1. 主 trunk 负责主体颜色
2. boundary geometry expert 负责 silhouette / alpha edge
3. boundary color expert 只做少量局部补偿
4. tiny repair / legacy fallback 只保留兜底，不再长期承担主输出职责

### 7. 当前最具体的待做清单

把上面 4 条方向压缩成可执行清单，就是下面这些：

1. 从 `v136a` 底座出发，优先做 boundary-aware geometry 路线，而不是继续做 `v138a` 这种 texture boundary head 加码版。
2. 显式启用并重构 boundary residual 通路，让 `_boundary_opacity_residual / _boundary_scaling_residual` 真正承担 hardest contour 的修边任务。
3. 新建 boundary-only hard mining 监督，把窄 band、top-k edge patch、silhouette outer 作为单独损失链，而不是继续挂在 interior detail 上顺带学。
4. 暂停继续推进“更强 legacy retirement / 更强 tiny repair 退场”这类实验，直到 boundary expert 已经被证明确实能稳定顶住 hardest edge。
5. 暂停继续堆叠新的 owner texture boundary head 小变体，除非先把 boundary 路由从 detached prior 改成 image-error-driven。

### 8. 到当前这一步的最终一句话

> `v137a / v137b / v138a` 这三版已经把事情说明白了：当前清晰度提不上去，不是因为还差一点 edge 权重，也不是因为 legacy 退得不够狠，而是因为 hardest blur 的主战场其实在 silhouette / alpha-edge / boundary routing 这条链路上；只要还主要在 texture owner 这边做小修，小改是能动指标的，但很难动到用户真正感知到的那种“质变清晰度”。

> 不再只相信“先验上哪里像边界”，而是开始把“当前这张图里哪里真的边界错了”也并到 boundary routing 里。

## 2026-04-21 中午补录：结合代码再收束一次 root cause，现在和 baseline 真正差的到底是什么

### 1. 为什么说当前 boundary 路由仍然主要是“后验修补”，不是“前向主导”

当前代码里最关键的几件事是：

1. `binding_boundary_score` 虽然在 `models/deformer/rigid.py` 的 `ExplicitBinding.forward()` 里会算出来
- 但它在 forward 末尾是直接 `detach` 后挂到 `deformed_gaussians`
- 它更像一个结构先验标签，不是前向形变主干的一部分

2. 真正混入图像误差的 `binding_boundary_mixed_score`
- 是在 `train.py` 里渲染完、和 GT 比完以后才构造出来的
- 它本质上是训练期的 routing / backward score
- 不是 forward deformation 本身的驱动量

3. boundary-aware backward 默认只给现有 Gaussian 参数和 boundary residual 挂梯度 mask
- `_xyz / _opacity / _scaling / _rotation`
- `_boundary_opacity_residual / _boundary_scaling_residual`
- 而且默认还会冻结 converter

4. 这意味着它更像：
- “当前 contour 已经长成这样了，我在现有点上修一点 alpha / scaling / 局部 residual”
- 而不是：
- “在 forward 里直接学一个可变形场，让 contour 先长对，再去渲染”

这也是为什么 `v139a -> v142e` 明明方向上一直没有错，但始终只能得到“有帮助、但不大”的结果。

### 2. 跟 baseline 相比，当前 explicit binding 仍然缺的不是一个小权重，而是一类前向自由度

把这件事说得更工程化一点：

1. baseline 那边的核心优势，不只是监督更强
- 而是前向里本来就有 learned rigid / skinning field
- 它允许 hardest contour 在 deformation 前向里被重新放到更合理的位置

2. 当前 explicit binding 的主干仍然是：
- cached anchor
- 固定/保守的 `anchor_weights`
- 由它们组合出来的 `T_lbs / x_bar`

3. 所以 boundary 这条线即便拿到了 signed image error
- 多数时候也只是驱动“现有点怎么修”
- 不是驱动“前向形变主干怎么重新长”

这就是当前和 baseline 最大的结构差异：

> baseline 的 hardest contour 更像是“前向生成出来的”，而 explicit binding 当前这条线更像是“先按旧 binding 生出来，再靠后端 boundary residual 去补”。

### 3. 为什么 `重新从 0 开始训练` 不是唯一答案，但 `只做晚期 resume` 也基本不够

到这里其实可以把之前几轮的歧义彻底说清楚：

1. 不是说“只要从 0 训，一切都会自动修好”
- 如果前向仍然没有新的可学习自由度
- 只是更早地重复同一套 conservative binding
- 那最多只是更早收敛到同一类模糊解

2. 但也不是说“晚期 resume 再修修 residual 就够了”
- `v139a -> v142e` 已经基本把这条线试透了
- 它可以修平均边界误差
- 很难打穿 hardest contour

3. 当前真正更像需要的是：
- 给 explicit binding 增加一个能直接作用在 forward deformation 上的 learnable residual field
- 让这条前向分支显式吃 boundary supervision
- 同时不要再把它限制成“只修旧点、densify 全关、converter 默认冻结”的纯后验修补 regime

因此，当前对 root cause 最准确的一句话是：

> 现在和 baseline 真正差的，不再主要是颜色 head、也不再主要是 unsigned / signed boundary schedule，而是 explicit binding 仍然缺一条“可学习的前向残差形变场”；只要 hardest contour 还主要依赖 cached binding + 后端 residual 修边，它就很难长成 baseline 那种硬轮廓。

## 2026-04-21 下午补录：回到代码本身，baseline 和 explicit binding 真正的结构差异已经可以写死

这一段补的是最新一轮代码复核后的正式结论。它不再只是经验判断，而是代码层面的结构差异。

### 1. baseline 的前向 deformation 是“可学习主干”

关键依据：

- `configs/rigid/skinning_field.yaml`
  - `rigid_lr: 1e-4`
- `models/deformer/rigid.py`
  - `SkinningField`
  - `self.lbs_network = get_skinning_mlp(...)`
  - `get_forward_transform()` 直接预测每个点的 skinning weights
  - `forward()` 里直接：
    - `T_fwd = self.get_forward_transform(...)`
    - `x_bar = torch.matmul(T_fwd, x_hat_homo)`

这意味着：

- baseline 的 hardest contour 不是主要靠后验修补
- 而是在前向里就由 learned skinning field 直接生成

### 2. explicit binding 的前向 deformation 仍然是“显式缓存 binding + 规则混合主导”

关键依据：

- `configs/rigid/explicit_binding.yaml`
  - 默认 `rigid_lr: 0.`
- `models/deformer/rigid.py`
  - `ExplicitBinding._get_binding(...)` 依赖 mesh 投影 / barycentric / cache
  - `_refresh_binding(...)` 在 `torch.no_grad()` 下执行
  - `forward()` 里 `canonical_xyz = ...detach()`
  - `T_lbs / T_dom` 仍然主要由 `anchor_weights / dominant_joint` 构造
  - `x_bar` 主要是：
    - `x_rigid`
    - `x_soft`
    - `x_free`
    - 再按 `layer_weights` 混出来

更重要的是：

- 现在已有的 boundary / residual 线，大部分仍然是：
  - 先生成现有 contour
  - 再做 routing / backward / residual repair

这和 baseline 的差异，不是一个小 schedule，而是 deformation 主干的范式差异：

> baseline 更像“learned forward field 主导，explicit prior 只是参考”；当前 explicit binding 更像“cached explicit prior 主导，learned residual 只是补丁”。

### 3. 这也解释了为什么 `rigid_lr` 只是晚期开一点，并不能自动变成 baseline

从 `v143 / v144` 的结果回看，问题已经很清楚：

1. 不是把一个小 MLP 接到 `anchor_weights` 后面，就等价于 baseline 的 skinning field
2. 不是把 `x_bar residual` 接进去，就等价于 baseline 的 learned support
3. 关键差在：
- 这些分支加入得太晚
- 作用域太小
- gate 太强
- 默认还是围着已有 contour 修

因此，真正更像 baseline 的修法，应该是：

- 让 learned forward branch 从一开始就是 deformation 主干的一部分
- explicit binding 负责提供：
  - 结构先验
  - 解释图
  - 区域语义
  - 编辑接口
- learned trunk 负责提供：
  - forward skinning flexibility
  - contour support placement

### 三个主因的重新排序

#### 1. 多视角采样稀释 / 训练密度不足

当前训练集约为：

```text
570 frames * 20 train cameras = 11400 samples
```

旧训练逻辑每个 iteration 只随机取一个 camera-frame：

```python
data_stack = list(range(len(scene.train_dataset)))
data_idx = data_stack.pop(randint(0, len(data_stack)-1))
data = scene.train_dataset[data_idx]
```

所以 15k iterations 的真实样本曝光约为：

```text
15000 / 11400 = 1.32 次 / 样本
```

即使累计到约 24k render exposure，也只有：

```text
24000 / 11400 = 2.1 次 / 样本
```

这和 mono 15k 的约 `26 次 / 样本` 不是一个训练密度。多视角下人能出来，但手臂、腰侧、衣服褶皱、脸部、鞋边等高频区域没有被充分拟合。

#### 2. SMPL / 相机小对齐误差 + 显式绑定偏软

整体对齐合理，但 768 分辨率下仍存在约 `5-16px` 的局部偏差。这个量级足够把边界、手臂、腰侧和衣服褶皱平均掉。

`v164b` 的 `sharpen_gate` 已经打开，但 `boundary_takeover` 很低，说明几何硬化开始工作，hardest contour 仍没有足够强的、稳定的梯度接管。

#### 3. 多视角颜色 / 曝光不一致

20 个训练相机亮度、白平衡、颜色质量不同。统一 texture MLP 会倾向解释平均颜色，质量差或偏色视角抽得太多时，会进一步压低纹理高频。

但后续 `v166/v166b` 说明：photometric correction 如果在主路径仍软的时候先上，会把颜色/边界误差解释成可校正项，反而削弱真实高频和轮廓梯度。
